# flowspace3 ↔ pij Rust-port architecture comparison

Reviewed flowspace3 `main` as the mold and a clean clone of pij `s108/rust-port` at `faf2f85cc9fd0fd8fd2432803e90d4177394c571`. Paths below are repository-relative and prefixed `fs3:` or `pij:`.

## 1. Convergent choices

- **Crate boundaries are the architecture.** Both use an eight-crate workspace and a committed dependency allow-list instead of folder-only layering (`fs3:Cargo.toml:1-21`, `fs3:crates/testkit/arch-allowlist.toml:1-29`; `pij:Cargo.toml:13-24`, `pij:crates/testkit/arch-allowlist.toml:1-30`).
- **Functional core, imperative adapters.** Both keep Tokio/SQL/HTTP out of core and put effects in adapter crates (`fs3:docs/how/architecture.md:13-24`, `fs3:crates/testkit/arch-allowlist.toml:44-56`; `pij:crates/testkit/arch-allowlist.toml:45-67`).
- **Explicit composition with `Arc<dyn Port>`, no DI container.** fs3 wires providers once in `AppState`; pij wires all seven ports once in `Services` (`fs3:crates/daemon/src/wiring.rs:1-17,135-188`; `pij:crates/daemon/src/lib.rs:43-89,117-199`).
- **Fakes are shipped infrastructure, not mock-framework output.** Both ban mocking libraries and run reusable contract suites through the same dynamic seam used in production (`fs3:docs/how/architecture.md:29-32`, `fs3:crates/testkit/tests/fakes_contract.rs:1-30`; `pij:crates/testkit/arch-allowlist.toml:32-43`, `pij:crates/testkit/src/contract.rs:1-15`).
- **`async-trait` is convergence, not a pij deviation.** Both need object-safe async trait objects while keeping core Tokio-free (`fs3:docs/how/architecture.md:68-86`; `pij:crates/core/src/ports.rs:14-23`, `pij:docs/plans/108-rust-port/assets/workshops/001-architecture.md:84-87`).
- **Durable live-row dedupe is the shared queue primitive.** Both collapse repeated submissions onto one pending/running row and free the key after settlement; Postgres uses `FOR UPDATE SKIP LOCKED`, while pij adds per-entity `serial_key` claiming for SQLite (`fs3:crates/store/src/jobs.rs:78-88,141-168`; `pij:crates/core/src/ports.rs:77-90`, `pij:docs/plans/108-rust-port/assets/workshops/001-architecture.md:24-29`).
- **The event wire is versioned NDJSON with an initial Hello and additive unknown kinds.** pij's v1-native `{v,at,kind,seat,payload}` intentionally follows the mold's `{v,at,kind,...}` family rather than freezing the TS `{seq,timestamp,type,data}` migration input (`fs3:crates/core/src/events.rs:12-36,64-103`; `pij:crates/core/src/wire.rs:107-166,176-215`, `pij:docs/plans/108-rust-port/assets/workshops/001-architecture.md:117-124`).
- **One installed artifact contains daemon and client.** Non-daemon commands remain daemon clients, preventing local CLI/daemon version skew (`fs3:crates/testkit/arch-allowlist.toml:217-234`; `pij:crates/cli/src/main.rs:1-5,45-92`).
- **Key publication ordering now converges: stage → bind → atomic publish → serve.** The brief's “fs3 publishes before bind” premise and pij workshop note are stale against current fs3 main. Both current implementations prevent (a) a client reaching a listener before its readable key exists and (b) a doomed second daemon overwriting the live daemon's key: binding reserves the transport but does not answer requests; publication occurs before `axum::serve` (`fs3:crates/daemon/src/boot.rs:78-82,554-564`, `fs3:crates/daemon/src/auth.rs:49-69`; `pij:crates/daemon/src/lib.rs:214-255`, `pij:crates/daemon/src/auth.rs:14-22`).

## 2. Divergences and verdicts

1. **`principled` — PostgreSQL/pgvector versus SQLite/WAL.** fs3's product is a central semantic index whose store needs Postgres, JSONB, vectors, and concurrent `SKIP LOCKED` workers; pij is machine-local orchestration state and gains zero-service installation from SQLite. pij correctly compensates for SQLite's actual failure modes by setting WAL on connection and centralising `BEGIN IMMEDIATE`, rather than pretending `busy_timeout` fixes deferred-lock upgrades (`fs3:Cargo.toml:66-69,92-103`, `fs3:crates/store/src/jobs.rs:141-168`; `pij:crates/store/src/migrate.rs:27-60,164-180`).
2. **`principled` — queue-first delivery.** fs3 queues expensive/retryable indexing while serving reads directly; pij makes temporary transport failure a durable, honest `Queued` outcome because its predecessor lost pre-bind messages. The broader use of the queue follows pij's delivery domain rather than cargo-culting fs3's endpoint split (`fs3:crates/store/src/jobs.rs:1-12,78-104`; `pij:docs/plans/108-rust-port/assets/architecture.md:67-74`, `pij:docs/plans/108-rust-port/assets/workshops/001-architecture.md:24-29`).
3. **`principled` — v1-native event schema.** Treating TS events only as migration input avoids making one cutover format pij's permanent wire contract; the chosen fields and unknown-kind policy are aligned with fs3's versioned event stream (`fs3:crates/core/src/events.rs:22-36,90-124`; `pij:docs/plans/108-rust-port/assets/workshops/001-architecture.md:117-124`, `pij:crates/core/src/model.rs:536-556`).
4. **`principled` — external-boundary ports.** `HarnessPort`, `TmuxPort`, `Transport`, and `LivenessPort` isolate genuinely varying harness/platform/process behavior; the seventh-port stop-and-ask demonstrates the seam was admitted from observed I/O rather than convenience (`fs3:docs/how/architecture.md:20-24`; `pij:crates/core/src/ports.rs:93-170`, `pij:docs/plans/108-rust-port/assets/workshops/001-architecture.md:73-75`).
5. **`principled` — `Registry`, `Spine`, and `Queue` are domain ports rather than fs3-style concrete store functions.** fs3 keeps queue/store concrete because its pure core does not orchestrate persistence; pij's core contract is the fleet's registry/history/work lifecycle itself, and the frozen capability seams permit deterministic fake/real selection without importing SQLite into core (`fs3:docs/how/architecture.md:20-24,176-185`; `pij:docs/plans/108-rust-port/assets/workshops/001-architecture.md:14-22`, `pij:crates/core/src/ports.rs:45-91`). This is a defensible domain exception to the mold's second-real-implementation rule.
6. **`drift` — real composition opens the same SQLite store three times.** The port split does not require separate pools, but `build_services` independently calls `pij_store::open` for Registry, Spine, and Queue; fs3 constructs one central pool and shares it (`fs3:crates/daemon/src/wiring.rs:79-87,187-188,360-362`; `pij:crates/daemon/src/lib.rs:125-143`). This adds repeated open/migration work and up to three four-connection pools without an architectural benefit.
7. **`principled` — fully fake default versus fs3's real database plus fake providers.** pij can model its seven boundaries in memory and benefits from selectively making one adapter real; fs3 cannot meaningfully fake pgvector/search semantics without inventing a second product. This is a domain-specific widening of the mold's offline-provider pattern (`fs3:docs/how/architecture.md:29-32,103-110`; `pij:crates/daemon/src/lib.rs:117-143,151-177`).
8. **`superior-adopt` — unknown event bytes are preserved, not merely tolerated.** fs3 deserialises an unknown kind to a unit `EventKind::Unknown`, losing the fields it did not understand; pij retains `kind` plus the original raw line so an old reader can forward a new fact losslessly (`fs3:crates/core/src/events.rs:201-206`; `pij:crates/core/src/wire.rs:107-126,201-215`). fs3 should adopt raw preservation at its consumer boundary.
9. **`superior-adopt` — the architecture gate is self-locating, lockfile-safe, and rationale-bearing.** fs3's gate resolves from compile-time `CARGO_MANIFEST_DIR` and invokes `cargo metadata --no-deps --offline`; its allow-list rows have no required rationale field. pij requires `why`, resolves the judged workspace at runtime, and separately performs a full `cargo metadata --locked` resolution, directly defending against a gate proving a different checkout or silently repairing a stale lock (`fs3:crates/testkit/src/arch.rs:476-512`, `fs3:crates/testkit/arch-allowlist.toml:54-56`; `pij:crates/testkit/src/arch.rs:205-217,501-535`, `pij:crates/testkit/src/lockfile.rs:1-31`). fs3 should take all three hardenings.
10. **No current divergence — key publication.** Historically, pij's post-bind atomic publication was `superior-adopt` because it caught second-daemon credential clobber (`pij:docs/plans/108-rust-port/assets/workshops/001-architecture.md:168-173`). Current fs3 main already implements the same ordering, so reporting this as an active divergence would be wrong (`fs3:crates/daemon/src/boot.rs:554-564`).

## 3. What pij should have taken but did not

- **Construct one real store pool, then clone/share it across the three views.** fs3 constructs its central `PgPool` once and every store operation receives that handle (`fs3:crates/daemon/src/wiring.rs:79-87,187-188,360-362`). pij independently opens the same path for Registry, Spine, and Queue (`pij:crates/daemon/src/lib.rs:125-143`, `pij:crates/store/src/migrate.rs:49-60`); even if the three traits remain, one `Pool<Sqlite>` can feed all three constructors and avoid up to 12 connections plus repeated migration/open work.
- **Promote the architecture map to the standing architecture front door.** fs3 moved implemented doctrine to `docs/how/architecture.md` and tells contributors to read it before adding a file (`fs3:docs/how/architecture.md:1-9`). pij's map remains under plan-108 assets with promotion explicitly deferred (`pij:docs/plans/108-rust-port/assets/architecture.md:1-9`), so later work outside that plan can miss the rules after the plan closes.

## 4. Confidence and limits

- **Confidence: high on implemented boundaries and the verdicts above.** Every claim was checked against code or committed architecture data on both sides, not inferred from crate names.
- pij was reviewed from a clean local clone of `s108/rust-port` at `faf2f85c`; the active worktree contained concurrent uncommitted edits, which were deliberately excluded. The brief's approximate `dab48c70` head is older.
- The clean snapshot still marks real Transport as wave-3 work (`pij:crates/daemon/src/lib.rs:146-154`), so this review does not classify the unfinished transport implementation, final CLI breadth, or post-wave-2 composition as drift.
- This was a read-only review. I did not run either workspace's gate because Cargo can update build/lock artifacts; flowspace3's harness boot also refused safely because `FS3_TEST_DATABASE_URL` was unset. The report therefore verifies architecture statically, not the brief's “181 tests / gate green” runtime claim.
- Current fs3 main contains the corrected post-bind publication code, but one test comment still says “publishes daemon.key before binding” (`fs3:crates/daemon/tests/health.rs:155-156`). The implementation and boot comments agree with each other; I treated the test comment as stale, not as behavior.
