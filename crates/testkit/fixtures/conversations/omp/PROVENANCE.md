## Line 0 is a fixed-width 256-byte title slot, rewritten IN PLACE — and it IS byte-stable

This is the property the cursor contract rests on, so it is stated with its evidence.

Every omp session file begins with a `title` record, not the `session` header, and that first line is padded to a constant width by a `pad` field of spaces. Line 0 of this fixture, verbatim (255 characters + newline = exactly 256 bytes):

    {"type":"title","v":1,"title":"","updatedAt":"2026-08-26T07:46:01.430Z","pad":"                                                                                                                                                                              "}

Measured across ALL 98 omp session files on this machine, spanning every cwd-slug directory under `~/.omp/agent/sessions/`:

- 98 of 98 files have `type":"title"` as line 0. There is no exception.
- 98 of 98 line-0 lengths are exactly 256 bytes including the newline. The set of distinct lengths has one element: `{256: 98}`.
- The pad absorbs the title exactly. For the key-set `{type, v, title, updatedAt, pad}`, `len(title) + len(pad) == 174` in every file; for `{type, v, title, source, updatedAt, pad}` it is `158` in every file. The 16-byte difference is precisely the inserted `,"source":"user"`. Observed titles range from 0 to 46 characters and pads from 174 down to 112 — the sum never moves.
- The rewrite is observable, not inferred. Six flowspace3 sessions carry 1 to 4 `title_change` records apiece; in every one, line 0's `title` equals the LAST `title_change` value in the file while line 0 is still exactly 256 bytes. Examples: `…01a03bb8` (1 change, line-0 title `base-pm`), `…01a03bf0` (4 changes, line-0 title `Re-review fix-0003 remediation`), `…01a03c4c` (1 change, line-0 title `Implement ElementKind and parser support`). The header was overwritten in place, repeatedly, at constant width.

**Verdict: byte-stable.** A title rewrite cannot change the file's total byte length. Byte offset 256 is the invariant start of line 1, and every offset from there on is unaffected by any number of title changes. A byte-offset cursor is therefore legal for this store, with one condition: it must not treat bytes 0..255 as append-only content. A cursor that reads line 0 once and never again serves a stale title forever, and any whole-file hash or `size == offset` "nothing changed" test is unsound, because the file mutates without growing. Recipe §3's blanket claim that all three file stores are APPEND-ONLY jsonl is false for omp in exactly this one region.

Not observed, therefore not claimed: what the writer does if a title exceeds the 158-character budget. The longest title on this machine is 46 characters, so the overflow path is unproven here.

## Recipe corrections

Three places where `09-ingestion-recipe.md` describes something this store does not do. Each is provable from the committed bytes.

1. **The omp session-directory slug strips the home prefix.** The directory is `-substrate-flowspace-flowspace3`, not the `-Users-agent-substrate-flowspace-flowspace3` form recipe §0 predicts when it says both claude and omp use "absolute path with `/` -> `-`". That convention is claude's alone. A resolver that builds the omp path from the claude rule finds no directory. Consequence visible here: sanitisation rule 2's derived-slug rewrite matched 0 times in this fixture, while the plain `/Users/...` rewrite matched 87 — the slug form simply never appears in omp paths. The `session` record's `cwd` (line 1) is the full absolute path, so the slug is derivable from the record but is NOT the record's own text.

2. **Compaction is a first-class `compaction` record type, not an injected user turn.** Gotcha 5 predicts an injected-instruction turn; omp emits a dedicated record. Line 184: `{"type":"compaction","id":"a932507b","parentId":"58a257ae","timestamp":"2026-08-26T08:14:24.462Z","summary":"## Goal\n…","shortSummary":"","firstKeptEntryId":"068a550c","tokensBefore":117001,"details":{"readFiles":[…],"modifiedFiles":[".agents/skills/flowspace/SKILL.md"]},"fromExtension":false}`. It sits IN the parent chain — line 185's `parentId` is `a932507b`, the compaction's own `id` — so a reader that allowlists only `message` records drops the sole marker that context was rebuilt AND breaks the chain across the seam. `firstKeptEntryId` names the first surviving entry and `tokensBefore` the pre-compaction context size; both are free discontinuity evidence that nothing else in the store provides.

3. **`toolName` lives on the paired `toolResult`, never on the call, and a mirror record precedes every call.** A `toolCall` content block names its tool under `name` (keys: `type`, `id`, `name`, `arguments`, `partialArgs`, `streamIndex`, `intent`); `toolName` appears only on the `toolResult` message and on the `custom` / `tool_execution_start` mirror. Keying calls on `toolName` yields nothing. The mirror is emitted BEFORE the assistant message that contains the call, so counting tool invocations across all record types double-counts by exactly 2x — 72 mirrors for 72 calls in this window. The trio a reader unit can prove all of this against is lines 5 → 7 → 8: line 5 is `{"type":"custom","customType":"tool_execution_start","data":{"toolCallId":"hYt33Fa96HJ9Rh7aucPDi083PTQCjVxQ","toolName":"read",…},"id":"da3c3e2c","parentId":"d137117f",…}`; line 7 is the assistant record carrying that call plus a second one (`AetaC18KfXpV58ymlfjtfmlvzyqBpFEp`, `name` `read`, `arguments.path` `skill://pij`); line 8 is the `toolResult` with `toolCallId` `AetaC18KfXpV58ymlfjtfmlvzyqBpFEp` and `toolName` `read`.
